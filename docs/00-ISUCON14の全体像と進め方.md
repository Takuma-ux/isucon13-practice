## 1. ISUCON は何をする大会か

制限時間内に、与えられた Web サービスを速く正しく動かす競技である。

ISUCON14 の題材は配車アプリ **Isuride** である。ユーザーがライドを依頼し、椅子（車両）が座標を送りながら迎えに行き、目的地まで運び、評価と決済をする。ベンチマーカーが大量の仮想ユーザーと椅子を動かして採点する。

点は「API が何回呼べたか」ではなく、だいたい次の連鎖で伸びる。

```
依頼がすぐマッチする
  → 近い椅子がすぐ迎えに来る
    → 実移動が椅子の速度どおり進む
      → 評価が高くなる
        → ユーザーが辞めず、評判で新規が増える
          → 売上が立ち、オーナーの椅子が増える
            → 同時に運べる人数が増える
```

今回のログにあった「マッチ待ち / 乗車地点まで / 実移動時間が不満」は、この連鎖のどこが遅いかを示す指標である。38656 点の走行ではマッチ待ち 0%、乗車 29%、実移動 91% だった。実移動がまだ本命の伸びしろである。

## 2. 「インフラ側」と「アプリ側」

よく言われる分担は次である。


| 側    | 触るもの                               | 典型作業                             |
| ---- | ---------------------------------- | -------------------------------- |
| インフラ | Nginx、MySQL、systemd、複数台分割、カーネル、TLS | ログ停止、接続数、バッファ、リバースプロキシ、DB を別マシンへ |
| アプリ  | Go / 言語実装、SQL、スキーマ                 | N+1 解消、INDEX、キャッシュ、ロック短縮、配車ロジック  |


公式初期構成はすでに Nginx → Go :8080 → MySQL になっている。インフラを「ゼロから組む」必要はない。やることは既存の Nginx / MySQL を**負荷向けに調整する**ことである。

### なぜアプリ修正だけで 38000 近くまで行ったか

今回の律速が、Nginx のワーカー数やディスクではなく **アプリが MySQL に出すクエリの量とロック時間** だったからである。

椅子は数十ミリ秒ごとに次を叩く。

- `POST /api/chair/coordinate`（現在地）
- `GET /api/chair/notification`（状態）
- `GET /api/app/notification`（ユーザー側の状態）

公式実装は、そのたびに「全ライドを取る」「status 履歴を 1 件ずつ見る」「クーポンを引き直す」といった重い SQL をしていた。ここを軽くすると、同じ 60 秒の中で椅子が何歩も余分に進む。実移動の不満が下がり、完走と売上が増え、椅子が増え、点が非線形に伸びる。

インフラ側で access_log を止めても、1 リクエストが SQL 10 本なら効果は小さい。逆に、アプリが 1 リクエスト 1〜2 クエリまで減ると、Nginx / MySQL のデフォルトでも数万点まで持つことがある。今回がまさにその形である。

`fa6fee1` には MySQL の `innodb_buffer_pool_size` や Nginx の access_log 停止も入っている。ただし 19414 → 38656 の跳ねは、その直後の **アプリ側メモリキャッシュとロック順の変更**（`f86b739`）が本体である。インフラ変更は「下駄」で、点数の主役ではなかった。

インフラが本格的に効くのは、だいたい次の段階である。

- アプリのホットパスが十分速いのに CPU が Nginx や TLS で埋まっている
- MySQL のディスク flush が律速
- 3 台あるのにアプリ・DB・ベンチが 1 台に同居している

50,000 点超（上位）を狙うと、複数台分割や接続チューニングの比重が上がる。30,000〜40,000 までは「遅い SQL とロック」を潰す方が先、というのがこの問題の実情である。

## 3. 大会で求められる修正の進め方

求められるのは「きれいな設計」より **測って、一点直して、再測る** ことである。

1. ベンチを 1 回回し、`pass` とスコアとエラーコードを記録する
2. ログの不満率・エラー（CODE=33 など）から、今いちばん痛い層を決める
3. そこだけ直す（コミットを小さくする）
4. 同じコマンドで再ベンチする
5. 点が上がり `pass` なら残す。落ちたら戻す

今回の 5 コミットはその実例である。

```
正しさ（CODE=33）を先に取る
  3b16aa5 → 500525c → 3619437
    （COUNT は正しいが重い → 点は 21000 から 19000 へ）

正しさを保ったまま軽くする
  fa6fee1（COUNT 廃止、即時配車、INDEX）
    （点はほぼ横ばい。ワーカー競合で少し下がった）

ホットパスのロックと認証を外す
  f86b739（メモリキャッシュ、決済中に椅子をロックしない）
    （19414 → 38656）
```

間違えた順は「速くしてから正しさを後回し」である。`getChairStats` を雑に `evaluation IS NOT NULL` にした時期は点が伸びても CODE=33 で信頼できなかった。大会では **fail（内容不一致・500）を残した高速化は、最終提出で死ぬ**。

優先順位の目安:

1. ベンチが落ちる（500、内容不一致）を潰す
2. いちばん多い API / いちばん遅い SQL を軽くする（今回なら notification と coordinate）
3. 点数に直結するドメイン処理（配車の割り当て）を変える
4. Nginx / MySQL のパラメータ
5. 複数台分割

「修正を加える」ときに毎回確認すること:

- 外部の JSON の形を変えていないか
- status の意味（MATCHING → ENROUTE → PICKUP → CARRYING → ARRIVED → COMPLETED）を飛ばしていないか
- 初期化（`POST /api/initialize` → `sql/4-index.sql`）で新列・INDEX が入るか
- 1 変更 1 ベンチになっているか
