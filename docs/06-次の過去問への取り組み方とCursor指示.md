# 次の過去問への取り組み方（一般手順）と Cursor への指示

対象: ISUCON の過去問を、Cursor の AI エージェントと一緒に進めるとき。  
目的: 「ボトルネックを直して」だけに頼らず、計測と当たり付けで差を開く。

関連: [ISUCON14 の全体像](./00-ISUCON14の全体像と進め方.md)

---

## 0. 最初に覚える原則

1. **1 変更 → 1 ベンチ → 記録**（まとめて直さない）
2. **fail（内容不一致・500）を残した高速化は捨てる**
3. AI には「直して」より **「測る → 仮説 → 案 → 実装 → 検証」** をやらせる
4. 人がやる仕事は **仮説と優先順位とレビュー**。実装の下書きは AI でよい

「他の参加者も AI に直させる」なら、差は次で付く。

- 何を測ったか
- なぜそこかを言語化できるか
- 直したあと何が改善したかを説明できるか
- 壊れたときにすぐ戻せるか

---

## 1. 初日〜最初の2時間（環境と全体像）

チェックリスト:

- [ ] リポジトリ／サーバに入れる。言語を1つに決める（Go など）
- [ ] 公式どおり初期ベンチが通る（`pass` の有無・スコア・エラーをメモ）
- [ ] マニュアル・採点の説明を読む（点が何で増えるか）
- [ ] 主要 API 一覧をコードから出す（`/api/...`）
- [ ] ドメインの「体験指標」があればメモする（例: マッチ待ち／乗車／実移動）

この段階で AI に頼む例:

```text
このリポジトリは ISUCON 過去問です。まだ最適化はしないでください。
やってほしいこと:
1. 言語実装のエントリポイントと主要 API 一覧
2. マニュアル／README から採点に効く指標を要約
3. 初期ベンチのコマンドと、見るべきログの場所
出力は短く、表形式で。
```

やってはいけない指示:

```text
ボトルネックを直してスコアを上げて
```

（計測も仮説もなく、大きな diff が出て戻しにくくなる）

## 2. 一般的な実装手順（繰り返しループ）

毎回この順で回す。

```
① ベンチ（または短い計測走行）
    ↓
② 事実を書く（スコア / pass / エラー / 不満率 or alp / slow）
    ↓
③ 仮説を1つに絞る（技術 or ドメイン）
    ↓
④ 最小の修正案を出す（ファイルと変更の意図）
    ↓
⑤ 実装 → ビルド → 再起動
    ↓
⑥ 同じ条件で再ベンチ
    ↓
⑦ 比較表を書いて残す → よければ commit
```



### ② 事実の取り方

**必ず取るもの（ベンチ）**

- `pass` / スコア / 種別エラー
- ドメイン指標があればそれ（不満率、完走数、離脱など）

**できれば取るもの（技術）**

- Nginx access_log + `alp`（多い API・合計時間）
- MySQL slow log + `pt-query-digest`（遅い SQL）

計測用にログを ON にしたら、計測後は OFF に戻す（本番走行の点に影響するため）。

### ③ 仮説の切り分け


| 観察                        | 疑う層                   |
| ------------------------- | --------------------- |
| 500 / CODE=xx（内容不一致）      | 正しさ（先に直す）             |
| 特定 API の count / sum が大きい | 技術（N+1、ロック、無駄 SELECT） |
| 体験指標が悪い（待ち・評価・売上）         | ドメイン（割当・順序・計算）        |
| API は速くなったが点が伸びない         | ドメイン or 別の律速          |


仮説は **1文** にする。

例:

- 「notification の COUNT がホットパスを重くし、実移動不満が高い」
- 「matching が RAND のため乗車地点までの不満が下がらない」



### ④〜⑦ 実装の粒度

- 1 コミットで触る関心をできるだけ狭くする
- 外部 JSON・ステータス意味は変えない
- 新列・INDEX は initialize 経路に載せる
- 点が下がったらそのコミットを戻す判断を早くする

## 3. 当たりの付け方（AI に渡す前に人がやること）

完全に空の「直して」より、次のどれか1つでも付けると精度が上がる。

### A. ベンチ結果を貼る

```text
直前のベンチ結果:
- pass=true スコア=19775
- マッチ待ち 23% / 乗車 29% / 実移動 95%
- エラー map[]

仮説: 実移動が律速。椅子の coordinate / notification が重い可能性。
最適化の実装はまだしない。まずコード上どの関数が1歩を進めているか対応表を出して。
```



### B. 計測結果を貼る

```text
alp の上位は次:
1. POST /api/chair/coordinate  count=... sum=...
2. GET /api/chair/notification ...

slow query 上位:
1. SELECT ... FROM rides ...

この事実に基づき、直すならどれが先か、理由付きで3案だけ。実装はまだ。
```



### C. 「調査のみ」と「実装」を分ける

調査:

```text
実装禁止。appGetNotification のクエリ数と、CODE=33 が起きうるレースを説明して。
前後の擬似コードで。
```

実装:

```text
方針は決まっている: COUNT をやめ、列キャッシュ + 現在ライド除外で CODE=33 を維持する。
変更ファイルは go/app_handlers.go のみ。
実装して。ベンチコマンドは後で自分が回す。
```



### D. レビュー役を明示する

```text
この diff をレビューして。
見てほしい点:
1. ベンチの内容不一致（特に stats）を壊していないか
2. ホットパスのクエリが増えていないか
3. initialize でスキーマが足りるか
指摘は優先度順。勝手に追加最適化しない。
```

## 4. Cursor への指示テンプレ



### テンプレ1: 現状分析（実装なし）

```text
ISUCON 過去問の練習です。実装は禁止。

【ベンチ結果】
（ログを貼る）

【やってほしいこと】
1. 事実の整理（点・エラー・ドメイン指標）
2. 技術ボトルネック候補とドメイン候補を分けて列挙
3. 次に潰すべき仮説を1つだけ推薦し、理由を3行以内
4. その仮説を検証する計測手順（alp / slow / 見る関数）

表形式。推測は推測と書く。
```



### テンプレ2: 関数対応の確認

```text
実装禁止。
ベンチの指標「〇〇」が悪い。
この指標がどの API / 関数の遅延で悪化するか、コードを辿って対応表を作って。
根拠は「ベンチの定義」と「コード上の状態遷移」に分けて書いて。
```



### テンプレ3: 最小実装

```text
仮説: （1文）
方針: （どう直すか1文）
制約:
- 外部 API の形は変えない
- ファイルはできるだけ限定: （パス）
- 1つの懸念（例: CODE=33）を壊さないこと
- 余計なリファクタ禁止

実装後、変更点・リスク・再ベンチで見る指標を短く書いて。
```



### テンプレ4: 結果の解釈

```text
修正後のベンチ結果:
（ログを貼る）

前回比で何が良く／悪くなったか。
仮説は正しかったか。
次の仮説を1つだけ。実装はまだ。
```



### テンプレ5: 差を付けるレビュー

```text
あなたは対戦相手の提出前レビューアです。
この変更で点は上がりそうだが、失格・減点になりうる点を厳しく挙げて。
代替案があれば「より安全な最小案」を1つ。
```

## 5. やってはいけない AI の使い方


| 悪い指示            | 起きやすいこと          |
| --------------- | ---------------- |
| 「全部速くして」        | 巨大 diff、原因不明の点下落 |
| 「インフラもアプリもまとめて」 | 何が効いたか分からない      |
| ベンチ結果を貼らずに「遅い」  | 的外れなキャッシュ・並列化    |
| fail を無視して高速化   | 最終提出で死ぬ          |
| 説明書を読ませずに連打     | 同じ失敗を繰り返す        |


人が差を付けるコツ:

- **仮説を自分が書く**（AI に書かせたあと、自分が採否する）
- **比較表を残す**（スコア・不満率・エラー）
- **戻せる単位で commit する**
- 「なぜその API か」を自分の言葉で言えるようにする

## 6. タイムボックスの目安（練習用）


| 時間     | やること                      |
| ------ | ------------------------- |
| 0〜30分  | 初期ベンチ・マニュアル・API 一覧        |
| 30〜60分 | 計測 or ドメイン指標の整理、仮説1つ      |
| 次の1時間  | 最小修正 → ベンチ → 記録           |
| 以降     | 同じループ。2回連続で点が動かなければ仮説を変える |
| 終盤     | fail 潰し、設定の永続化、説明できる状態にする |


大会本番では「終盤の安全」が特に重要。練習でも最後の30分は計測ログを戻す・サービス再起動確認を入れる。

## 7. 1回のループの記録フォーマット（コピー用）

```markdown
## 走行 N
- 日時:
- コミット / 変更概要:
- スコア / pass / エラー:

- 結果（仮説は当たったか）:
- 次:
```

## 8. このリポジトリ（ISUCON14）で得た教訓の再利用

次の過去問でも型は同じ。中身だけ差し替える。


| 今回やったこと                           | 一般化                       |
| --------------------------------- | ------------------------- |
| 実移動不満 → coordinate / notification | 体験指標 → 状態を進める API をコードで辿る |
| CODE=33 を先に直す                     | 正しさ → そのあと同じ意味で軽くする       |
| COUNT 廃止・ロック短縮・認証キャッシュ            | ホットパスのクエリ量とロック時間          |
| 即時配車・距離優先                         | ドメイン（割当の質）                |
| 「直して」だけよりベンチ貼り                    | AI には事実と仮説と制約を渡す          |


---



## 9. 最短の実践フレーズ（覚える用）

1. まずベンチ結果を貼る
2. 「実装禁止で、仮説を1つ」
3. 「その仮説の最小実装、ファイル限定」
4. 再ベンチ結果を貼り「仮説の検証と次の1手」
5. 怪しい diff は「失格観点でレビュー」

これだけで、「ただ直してください」より再現性と得点が安定する。
